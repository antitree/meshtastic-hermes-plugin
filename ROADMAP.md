# Roadmap

Work deliberately deferred, with the reason. Items are grouped by what makes
them hard, not by priority.

## Deferred tests — need hardware, a browser, or a real Hermes host

These are out of scope for the automated suite: each needs an external
dependency CI cannot provide. The current suite covers the same code paths
against fakes, so the gap is *fidelity*, not coverage.

| Test | What makes it hard |
|---|---|
| Real radio over TCP (`TCPInterface` against a physical node) | Needs a Meshtastic device on the network; CI has no radio and no LoRa spectrum. |
| On-air send/receive round trip between two nodes | Needs two radios in RF range, plus regulatory-legal transmission on a shared medium. |
| PKI (end-to-end) DM encryption verified on the wire | Needs two provisioned nodes with real keypairs; the crypto lives in device firmware, not in this package. |
| Delivery-ack (`onResponseAckPermitted`) against real firmware | The ACK is generated by firmware routing; only its client-side handling is testable here (and is covered with a fake). |
| Multi-hop / lossy-link behavior, hop-limit decrement | Needs a physical multi-node mesh; cannot be simulated meaningfully in-process. |
| `MeshtasticAdapter` against the **real** `BasePlatformAdapter` | Needs a Hermes Agent checkout. The suite stubs `gateway.platforms.base`; see the caveat below. |
| Full gateway loop (Hermes agent → LLM → radio reply) | Needs a running Hermes gateway plus an LLM backend. |
| `hermes plugins install` / the Hermes plugin security scanner | Needs the Hermes CLI. Tracked separately as WT1. |
| REPL interactive behavior (arrow-key history, Ctrl-R) | Needs a PTY and a real `readline`; `input()` is stubbed instead, so the dispatch logic is covered but the terminal UX is not. |

### The stub-gateway caveat — read this before trusting `test_adapter_runtime.py`

`meshtastic_platform.adapter` only defines `MeshtasticAdapter` when
`gateway.platforms.base` and `gateway.config` import, which they do not outside
Hermes. `tests/test_adapter_runtime.py` installs a **stub** gateway package into
`sys.modules` and re-imports the adapter against it.

That verifies this adapter's own logic against the base-class surface it uses
(`_set_fatal_error`, `_mark_connected`, `build_source`, `handle_message`,
`SendResult`, `MessageEvent`, `MessageType`). It does **not** verify that the
stub matches real Hermes. **If the real base class has a different signature,
these tests still pass.** Notably, `connect()` here takes no arguments, and
there is reason to think the real contract differs — that is WT2's subject.

## Lint is advisory, not gated

`pyproject.toml` configures ruff with only `line-length` and `target-version` —
no `[tool.ruff.lint] select`. Ruff therefore lints with whatever its default
rule set happens to be, and that set has grown since `ruff>=0.4` was pinned. On
ruff 0.16 the **unmodified** upstream tree reports ~76 findings (`BLE001`,
`S110`, `SIM103`, `RUF100` …) in code no recent change touched.

The CI lint step is therefore `continue-on-error: true`. Making it a gate needs
an explicit, maintainer-chosen `select` list first — a decision about shared
project config rather than a CI change. Test files added for CI are lint-clean
under the current default rules.

## Coverage exceptions

Line coverage is at 100%, but four constructs are excluded rather than tested,
because a test for them would assert nothing real:

- `if __name__ == "__main__":` in `meshtastic_hermes/__main__.py` — excluded via
  `exclude_also`. The module entry point *is* covered, by a real subprocess test
  (`test_module_is_runnable_as_python_dash_m`); only the guard line is skipped.
- `if _REPO_ROOT not in sys.path:` in `meshtastic_platform/adapter.py` — an
  import-time shim that runs before pytest can observe it, and is exercised
  implicitly by every cross-package import.
- `except Exception: text = None` around `payload.decode("utf-8", "replace")` in
  `observer.py` — `errors="replace"` cannot raise, so the branch is dead.
  Marked `pragma: no cover` inline.
- `except ImportError` around `import readline` in `__main__.py` — readline is
  absent only on some Windows builds. Marked `pragma: no cover` inline.

Coverage is **reported, never gated**. There is deliberately no
`--cov-fail-under`: a coverage gate pushes contributors toward hollow tests on
error branches to hit a number, which is the opposite of the intent.

## Known behavior gaps (not test gaps)

Carried over from the handoff; these are missing *features*, and the tests
correctly document today's behavior rather than the desired behavior.

- **Transmit rate limiting: done.** Item 3 of `docs/security-remediation.md`,
  shipped as `meshtastic_hermes/rate_limit.py`. This superseded the earlier
  decision not to build an airtime layer: the remediation plan requires it as a
  loop breaker, and it had to cover manual tool sends, which the earlier framing
  did not.

  What actually shipped:

  - One process-wide limiter covering every outbound path — `meshtastic_send_text`,
    gateway adapter replies, and bridge `--send`. All three funnel through
    `tools.send_text`, so the check has a single choke point, placed after item 1's
    send policy authorizes the destination and before any `iface.sendData`.
  - Sliding-window buckets keyed three ways — global, `dm:<node id>`, and
    `ch:<index>` — plus a per-destination cooldown. Every applicable bucket must
    admit a packet, and a refusal charges nothing.
  - **One token per transmitted packet, not per logical reply.** A chunked reply
    spends a token per part, because each part is real airtime. Parts 2..n are
    exempt from the *cooldown* (they are one turn, not several) but are still
    charged; running out mid-reply drops the remaining parts and reports failure.
  - Shared across both copies of the package via a fixed `sys.modules` slot, the
    same construction `connection.py` uses — Hermes loads the tools plugin under a
    mangled name while the adapter imports `meshtastic_hermes` top-level, so a
    module global would have given each path its own bucket.
  - `MESHTASTIC_MAX_SENDS_PER_MINUTE` (10), `MESHTASTIC_MAX_CHANNEL_SENDS_PER_MINUTE`
    (5), `MESHTASTIC_MAX_DM_SENDS_PER_MINUTE` (6),
    `MESHTASTIC_REPLY_COOLDOWN_SECONDS` (5). All fail closed — an invalid or
    non-positive value falls back to the default, and there is no "unlimited".
  - Tools return `{"error": "rate_limited", "retry_after_s": …, "scope": …}`;
    adapter replies return `SendResult(success=False, error="rate_limited")` and log
    the scope and retry delay. The effective budget is logged at every connect.
  - Monotonic time, injected as `time_fn`, so the tests are deterministic under
    fake time and a wall-clock step cannot mint free transmissions.

  Still open: there is no bot-to-bot *detection*, only a bound on the loop. And the
  limiter is per-minute, so it does not give the test rig the per-run budget
  `--transmit` needs (see below).
- **Mention gating.** `MESHTASTIC_REQUIRE_MENTION` (on by default) requires a
  channel message to start with this node's short name, long name, or node id.
  DMs are always answered. This is a gate on which messages are answered, not a
  transmission budget — the budget is the rate limiter above. Both matter: gating
  keeps the exchange from starting, the limiter keeps it from running away.
- **The rig's transmit check is unimplemented.** `--transmit` exists but reports
  `NOT_IMPLEMENTED`: both candidate send paths either open a second TCP
  connection to a node that accepts one client, or drive the live gateway on a
  real channel. The plugin's rate limiter does not unblock it — that is a
  per-minute ceiling, and the rig needs a per-run cap it enforces itself, plus a
  dedicated test channel on the radio.

## Security scanner — not tracked

We do not track the Hermes plugin scanner's verdict, and CI does not run it.

The scanner (`tools/plugin_guard.py`) is regex matching over raw file text —
no parsing, no dataflow, no semantics. In practice that means it flags a
`| Env |` Markdown table header as "exfiltration", the word `sudo` in a NixOS
instruction as privilege escalation, and the documented procedure for enabling
a plugin as "persistence". Hermes' own plugin-authoring guide scores
`dangerous` under it.

Satisfying it required changing byte sequences rather than behavior, which
bought no safety and taxed documentation clarity, so we stopped. Write the
docs to be clear.

`scripts/hermes_scan.py` and `docs/security-scanner.md` are kept for reference
— run the script by hand if you ever want to see the verdict — but nothing
gates on them.

**Consequence to know:** `hermes plugins install` performs its own scan and
will still refuse this plugin on a `dangerous` verdict (`--force` does not
override). Install via symlink (`just link`) or Nix, as the docs describe.

## Release automation — what is NOT verified until the first real run

`scripts/bump_version.py` is unit-tested (`tests/test_version_bump.py`) and the
two workflows pass `actionlint` and parse as YAML, but a release workflow cannot
be exercised locally. The following are verified only when they first run for
real, and the first merged PR / first manual dispatch should be watched:

- **The push to `main`.** Whether `GITHUB_TOKEN` can push depends on repository
  settings ("Read and write permissions" for Actions) and on branch protection.
  If `main` is protected without an exemption for `github-actions[bot]`, the
  push is rejected and the bump job fails *after* rewriting the files.
- **Tag creation and `gh release create --verify-tag`.**
- **The `concurrency: version-bump` serialisation** under two PRs merging
  seconds apart.
- **`[skip ci]` behaviour.** GitHub honours the marker for `push`/`pull_request`
  triggers; neither of these workflows listens to those, so today it is
  documentation of intent plus insurance (see below).

### The failure mode to watch for: a PAT silently removing a loop guard

The bump commit is protected from retriggering by three independent layers:

1. Neither workflow listens to `push`, so their own commit is not a trigger.
2. Pushes authenticated with `GITHUB_TOKEN` do not trigger workflow runs —
   GitHub's own guarantee.
3. `[skip ci]` in the commit subject, plus a `Refuse to bump our own bump
   commit` step that inspects `HEAD` and exits early.

Layer 2 is the one that disappears without any error message. If branch
protection is ever tightened so that `github-actions[bot]` cannot push and the
workflow is changed to use a PAT or a GitHub App token instead, **that push
does trigger workflows** — layer 2 is gone and nothing reports it. Layers 1 and
3 are what still hold in that world, which is why both are present even though
layer 2 alone closes the loop today. If a PAT is ever introduced here, re-read
this section before also adding a `push:` trigger.
